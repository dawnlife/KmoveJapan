# Q1. 자바에서 패키지(Package)의 정의와 목적은 무엇이며, 패키지 선언 시 전 세계적으로 고유한 이름을 짓기 위해 실무에서 사용하는 관례는 무엇인가?
## 1. 패키지(Package)의 정의와 목적
### 📦 정의
자바에서 패키지란 서로 관련이 있는 클래스(Class), 인터페이스(Interface) 등을 하나의 디렉터리(폴더) 단위로 묶어서 관리하는 그룹화 기구입니다.
### 🎯 목적
- 클래스 이름 충돌 방지: 대규모 프로젝트나 오픈소스 라이브러리를 가져다 쓰다 보면 서로 다른 개발자가 우연히 같은 이름의 클래스를 만들 수 있습니다. 패키지는 고유한 네임스페이스(Namespace)를 제공하여 이름이 같더라도 패키지 경로가 다르면 충돌 없이 사용할 수 있게 해줍니다.
- 접근 제어를 통한 캡슐화: 자바의 접근 지정자 중 default와 protected는 패키지 단위를 기준으로 작동합니다. 이를 통해 같은 패키지(모듈) 내에서만 부품처럼 공유하고, 외부 패키지에서는 접근하지 못하도록 끊어내어 정보 은닉과 캡슐화를 달성할 수 있습니다.
- 유지보수성 및 가독성 향상: 수백, 수천 개의 소스 파일을 역할(도메인, 기능)별로 분류하여 저장하므로, 향후 코드를 수정하거나 탐색할 때 원하는 파일을 빠르게 찾을 수 있어 프로젝트의 유지보수 비용이 낮아집니다.

## 2. 전 세계적으로 고유한 패키지 이름을 짓는 실무 관례
실무에서는 전 세계의 수많은 자바 라이브러리와 내 코드가 절대 겹치지 않도록 "인터넷 도메인 이름 역순(Reverse Domain Name)" 방식을 표준 관례로 사용합니다. 도메인은 전 세계에서 유일성이 보장되기 때문입니다.

### 🌐 명명 규칙 및 공식
[조직의 도메인 역순] . [프로젝트 이름] . [모듈/레이어 이름]
- 모두 소문자 사용: 패키지 이름은 관례적으로 대문자를 섞지 않고 전체 소문자로 작성합니다.
- 언더바(_) 자제: 도메인에 하이픈(-)이 포함되어 있다면 자바 식별자 규칙에 맞게 언더바(_)로 변경하거나 생략합니다.

### 💻 실무 적용 예시

# Q2. import문이 자바 컴파일러와 프로그램 성능(메모리 및 실행 속도)에 미치는 영향에 대해 설명하고, import com.project.*; 표현이 해당 패키지 내부의 하위 패키지 클래스까지 모두 가져오는지 서술하시오.
## 1. import문이 컴파일러와 프로그램 성능에 미치는 영향
결론부터 말씀드리면, import문은 컴파일 타임에만 영향을 미치며, 프로그램의 런타임 성능(메모리 및 실행 속도)에는 전혀 영향을 주지 않습니다.

- 자바 컴파일러(javac)에 미치는 영향: 자바에서 import문은 단순히 "소스 코드에 적힌 클래스 이름의 풀 패키지 경로(FQCN: Fully Qualified Class Name)를 컴파일러에게 알려주는 안내 역할"만 합니다. import문을 많이 작성하거나 와일드카드(*)를 사용하면 컴파일러가 해당 클래스를 찾는 데 약간의 시간을 더 소모할 수 있으므로 컴파일 속도가 미세하게 느려질 수는 있습니다.
- 런타임 성능(메모리 및 실행 속도)에 미치는 영향: 컴파일이 완료되어 생성된 .class 바이트코드 파일에는 import문이 모두 사라지고, 클래스 이름들이 java.util.ArrayList와 같이 전체 패키지 경로로 치환되어 들어갑니다. 따라서 자바 가상 머신(JVM)이 프로그램을 실행할 때는 import문으로 인한 메모리 추가 낭비나 실행 속도 저하가 0%도 발생하지 않습니다.

## 2. import com.project.*; 표현과 하위 패키지의 관계
❌ 결론: 하위 패키지 내부의 클래스까지 가져오지 못합니다.

자바에서 패키지 구조는 디렉터리(폴더) 형태로 계층화되어 보이지만, 문법적으로는 완전히 독립된 네임스페이스로 취급됩니다.

예를 들어 패키지 구조가 다음과 같다고 가정해 보겠습니다.

- com.project.MainClass
- com.project.sub.SubClass (하위 패키지 sub 내부의 클래스)

이 상황에서 import com.project.*;를 선언하면, com.project 바로 아래에 있는 MainClass만 인식될 뿐, 하위 패키지 폴더인 sub 내부의 SubClass는 자동으로 가져오지 못합니다. 따라서 하위 패키지의 클래스까지 사용하려면 아래와 같이 하위 패키지 경로를 명시하여 별도로 import 해주어야 합니다.

# Q3. 자바 프로그래밍 시 import문을 생략하고도 자유롭게 사용할 수 있는 클래스 부류 두 가지를 서술하시오.
## 1. java.lang 패키지에 속한 클래스들
자바에서 가장 기본적이고 필수적으로 사용되는 클래스들을 모아놓은 java.lang 패키지는 개발자가 별도로 import하지 않아도 자바 컴파일러가 자동으로 import 문을 추가해 줍니다.

- 설명: 프로그램 개발 시 핵심적으로 쓰이는 클래스들이기 때문에, 매번 import를 적어야 하는 번거로움을 줄이고 코드를 간결하게 유지하기 위해 자바 언어 차원에서 내장한 규칙입니다.

- 대표적인 클래스 예시:

  - String, StringBuffer, StringBuilder (문자열 처리)

  - System (콘솔 출력 System.out.println() 등에 사용)

  - Object (자바의 최상위 클래스)

  - Math (수학 계산)

  - Integer, Double, Boolean (기본 타입을 객체로 감싸는 래퍼 클래스)

## 2. 현재 클래스와 "동일한 패키지"에 있는 클래스들
자바는 소스 코드 맨 위 부모 디렉터리를 정의하는 package 선언을 기준으로 작동합니다. 같은 패키지(동일한 폴더/디렉터리) 내에 존재하는 클래스들끼리는 서로를 자유롭게 인지할 수 있습니다.

- 설명: 패키지는 일종의 독립된 모듈이자 가방입니다. 같은 가방 안에 들어있는 부품들은 굳이 외부에서 찾아올 필요가 없기 때문에 import문 없이 클래스 이름만으로 즉시 객체를 생성하고 호출할 수 있습니다.

- 실무적 예시 (영진 님의 GoCafe 프로젝트 기준):

  - 만약 com.github.dawnlife.gocafe.search 패키지 안에 CafeSearchService.java와 OpenSearchConfig.java가 함께 들어있다면, CafeSearchService 안에서 OpenSearchConfig를 불러올 때 import문을 생략할 수 있습니다.

# Q4. 서로 다른 패키지에 이름이 완전히 동일한 클래스가 각각 존재할 때(예: java.util.Date와 java.sql.Date), 이를 한 소스 파일 안에서 동시에 모두 사용해야 하는 경우 어떻게 코드를 작성해야 하는지 서술하시오.
서로 다른 패키지에 이름이 완전히 동일한 클래스가 존재할 때, 한 소스 파일 안에서 두 클래스를 동시에 사용하려면 클래스 이름 앞에 패키지 경로를 전부 붙여주는 '풀 패키지 경로(FQCN: Fully Qualified Class Name)' 방식으로 코드를 작성해야 합니다.

자바는 파일 최상단의 import문을 통해 클래스 경로를 생략할 수 있도록 돕지만, 동일한 이름을 가진 두 클래스를 모두 import하면 컴파일러가 어떤 클래스를 가리키는지 구분할 수 없어 이름 충돌(Name Collision) 및 컴파일 에러를 발생시킵니다.
```JAVA
import java.util.Date; // 자주 사용하는 util 패키지의 Date는 import 선언

public class DateExample {
    public void processDates() {
        // 1. import한 클래스는 평소처럼 클래스 이름만으로 사용 가능
        Date utilDate = new Date(); 
        System.out.println("기본 날짜 객체: " + utilDate);

        // 2. 이름이 중복되는 다른 클래스는 풀 패키지 경로(FQCN)를 직접 명시
        java.sql.Date sqlDate = new java.sql.Date(System.currentTimeMillis());
        System.out.println("SQL 데이터베이스용 날짜 객체: " + sqlDate);
    }
}
```
**물론 두 클래스 모두 import문을 쓰지 않고, 코드 내부에서 둘 다 java.util.Date와 java.sql.Date로 명시해도 문법적으로는 완전히 올바르게 작동합니다.**

# Q5. 자바 5부터 도입된 import static문(정적 임포트)의 개념과 기존 import문과의 차이점을 설명하고, 실무에서 정적 임포트를 사용할 때 주의해야 할 점은 무엇인지 서술하시오.
## 1. import static문의 개념과 기존 import문의 차이점
### 💡 개념
일반적인 import문이 특정 패키지의 클래스를 가져오는 역할이라면, import static문은 클래스의 static 멤버(필드, 메소드)를 가리켜 직접 가져오는 역할을 합니다. 이 문법을 사용하면 정적 멤버가 속한 클래스 이름을 생략하고, 마치 현재 클래스 내부에 정의된 멤버처럼 이름만으로 호출할 수 있습니다.

### 🔄 기존 import문과의 결정적인 차이점

- 기존 import문: import java.lang.Math;와 같이 클래스를 가져오므로, 내부 정적 메소드를 쓸 때 반드시 Math.max(a, b)처럼 클래스명(Math)을 앞에 붙여야 합니다.

- 정적 import문: import static java.lang.Math.max; 또는 import static java.lang.Math.*;로 정적 메소드를 직접 가져오면, 클래스명을 과감히 생략하고 코드 안에서 즉시 max(a, b)로 호출할 수 있습니다.

## 2. 실무에서의 구체적인 사용 예시 (영진 님의 프로젝트 기준)
영진 님이 진행하신 GoCafe(추천 플랫폼) 메인 프로젝트나 RateMate(환율 앱) 소스 코드의 품질을 높이기 위해 실무에서는 특히 두 가지 영역에서 정적 임포트를 적극 활용합니다.

### ① 단위 테스트(Unit Test) 작성 시 (가장 핵심적인 활용)
영진 님이 중시하시는 "격리되고 안전한 단위 테스트"를 작성할 때, 검증 라이브러리인 AssertJ의 assertThat()이나 Mockito의 가짜 객체 메소드들을 호출할 때 필수로 쓰입니다.
```JAVA
// 🛠️ 정적 임포트 선언
import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.Mockito.mock;

public class CafeSearchServiceTest {
    @Test
    public void 검색_테스트() {
        // 원래는 Assertions.assertThat(...) 또는 Mockito.mock(...)으로 써야 하지만
        // 정적 임포트 덕분에 클래스명을 생략하여 비즈니스 논리에만 집중할 수 있습니다.
        CafeSearchService mockService = mock(CafeSearchService.class);
        assertThat(mockService).isNotNull();
    }
}
```
### ② 공통 상수(Constant) 및 에넘(Enum) 참조 시
오픈서치(OpenSearch) 환경 구축 시 전역적으로 공유되는 타임아웃 시간, 가중치 값 등 static final 상수들을 모아둔 클래스가 있다면 정적 임포트로 코드를 깔끔하게 다듬을 수 있습니다.

## 3. 실무에서 정적 임포트 사용 시 반드시 주의해야 할 점

import static문은 코드를 간결하게 만들어 주지만, 남용할 경우 오히려 영진 님이 지향하시는 "팀 전체가 유지보수하기 좋은 직관적인 구조"를 해치는 양날의 검이 될 수 있으므로 다음 사항을 엄격히 통제해야 합니다.

- 이름 충돌과 가독성 저하 (가장 치명적): 한 소스 파일 안에서 서로 다른 두 클래스의 정적 메소드를 동시에 정적 임포트했는데, 하필 두 메소드의 이름이 같다면 자바 컴파일러는 어떤 것을 실행해야 할지 몰라 에러를 냅니다. 에러가 나지 않더라도 클래스명이 안 보이기 때문에 "이 sort()가 어떤 정적 도구에서 실행된 거지?"라며 팀원들이 코드를 읽을 때 혼란을 겪게 됩니다.

- 적절한 허용 기준 마련: 실무 및 구글 자바 스타일 가이드에서는 정적 임포트의 범위를 JUnit/AssertJ 테스트 코드, 또는 프로젝트 전체에서 공인된 전역 상수 클래스 정도로만 제한하여 사용하고, 일반적인 도메인 비즈니스 로직 클래스에서는 가독성을 위해 클래스명을 직접 명시하는 것을 권장합니다.

- **Q1. 외부 패키지 `com.service`에 정의된 `UserService` 클래스를 인스턴스화하여 사용하고자 한다. 파일 상단에 필요한 임포트 구문의 빈칸을 채우시오.**
    
    ```
    [      ] com.service.UserService;
    
    public class Controller{
        UserService service = new UserService();
    }
    ```
    
    - 완전한 소스 코드:Java
        
        ```
        import com.service.UserService;
        
        public class Controller{
            UserService service = new UserService();
        }
        ```
        
        설명: 다른 패키지에 있는 특정 클래스를 단순 참조하여 사용하고자 할 때는 클래스 선언부 위쪽에 `import` 키워드와 함께 해당 클래스의 전체 경로를 명시해야 한다.
        
- **Q2. `java.util` 패키지 안에 있는 `List`, `ArrayList`, `Map`, `HashMap` 등 모든 클래스를 개별 지정 없이 한 줄로 한꺼번에 임포트하기 위한 빈칸을 완성하시오.**
    
    ```
    import java.util.[   ];
    ```
    
    - 완전한 소스 코드:Java
        
        ```
        import java.util.*;
        ```
