# ◆ 자바 접근 지정자 기본 개념 문제 ◆

접근 지정자는 클래스, 멤버 변수, 메서드의 접근 범위를 제한하여 외부의 무분별한 수정으로부터 데이터를 보호하고, 객체 간의 결합도를 낮추는 객체지향 캡슐화(Encapsulation)의 핵심 장치이다.

---
## Q1. 자바의 4가지 접근 지정자(public, protected, default, private) 각각의 접근 허용 범위를 명확히 서술하시오.
### 🔒 private
- 허용 범위: 동일한 클래스 내부에서만 접근이 가능합니다. (getter, setter로 접근 가능)
- 특징: 외부 클래스(심지어 같은 패키지 내의 클래스 포함)에서는 절대 접근할 수 없습니다. 객체의 상태를 안전하게 보호하기 위해 필드 선언 시 가장 적극적으로 권장되는 제한자입니다.

### 📦 default (package-private)
- 허용 범위: 동일한 패키지 내부에 있는 클래스들 사이에서만 접근이 가능합니다.
- 특징: 접근 제한자를 아무것도 명시하지 않았을 때 적용되는 기본값입니다. 패키지가 다르면 접근이 불가능합니다.

### 🛡️ protected
- 허용 범위: 동일한 패키지 내부 + 다른 패키지에 있더라도 해당 클래스를 상속받은 자식 클래스에서 접근이 가능합니다.
- 특징: 상속 관계(IS-A 관계)에서 부모 클래스의 멤버를 자식 클래스에게 물려주고 재정의(Override)할 수 있도록 허용할 때 주로 사용됩니다.

### 🌐 public
- 허용 범위: 프로젝트 내부의 모든 클래스에서 제한 없이 접근이 가능합니다.
- 특징: 어디서나 접근할 수 있는 완전한 개방 상태를 의미합니다. 주로 외부에 노출해야 하는 공용 메소드(API)에 사용되며, 필드에 남용할 경우 데이터 무결성이 쉽게 훼손될 수 있으므로 주의해야 합니다.

|접근 제한자|동일 클래스|동일 패키지|자식 클래스 (타 패키지)|전체 (전체 패키지)|
|--|--|--|--|--|
|public|O|O|O|O|
|protected|O|O|O|X|
|default|O|O|X|X|
|private|O|X|X|X|

## Q2. 객체지향 프로그래밍에서 캡슐화(Encapsulation)의 정의와, 캡슐화를 달성하기 위해 접근 지정자를 활용하는 일반적인 클래스 설계 공식을 서술하시오.
### 1. 캡슐화(Encapsulation)의 정의
객체지향 프로그래밍(OOP)에서 캡슐화(Encapsulation)란 객체의 구체적인 데이터(필드)와 그 데이터를 처리하는 함수(메소드)를 하나의 단위(클래스)로 묶는 것을 의미합니다.

이때 핵심은 내부의 상세한 구현이나 데이터 구조를 외부에 노출하지 않고 감추는 정보 은닉(Information Hiding)에 있습니다. 외부 클래스에서는 객체가 제공하는 공용 메소드를 통해서만 객체와 소통할 수 있으며, 객체 내부가 어떻게 작동하는지 알 필요가 없도록 설계하는 것이 캡슐화의 본질입니다.

### 2. 캡슐화를 달성하기 위한 일반적인 클래스 설계 공식
실무 및 자바 표준 아키텍처 설계에서 캡슐화를 올바르게 실천하기 위해 사용하는 공공연한 규칙(공식)은 다음과 같습니다. 데이터의 오염을 방지하고 시스템의 유지보수성을 극대화하기 위해 이 방식을 표준으로 삼습니다.

#### ① 모든 인스턴스 필드는 private으로 선언한다
외부에서 객체의 상태(필드)에 직접 접근하여 값을 바꾸거나 읽지 못하도록 철저하게 빗장을 걸어 잠급니다. public으로 필드를 열어두면 외부에 강하게 결합되어 향후 필드명을 바꿀 때 모든 코드를 수정해야 하거나 비정상적인 데이터가 주입되는 대형 사고가 발생할 수 있습니다.

#### ② 필드에 접근할 수 있는 public Getter / Setter 메소드를 제공한다
필드를 숨긴 대신, 외부에 안전하게 데이터를 제공하거나 변경할 수 있는 창구(메소드)를 public으로 열어줍니다.

- Getter (접근자): 내부 필드의 값을 안전하게 읽어가도록 반환합니다.

- Setter (설정자): 외부에서 값을 변경할 때 사용합니다. 반드시 내부에 유효성 검사(Validation) 로직을 포함시켜 조건에 맞지 않는 잘못된 데이터(예: 음수 나이, null 값 등)가 객체 내부에 주입되는 것을 원천 차단합니다.

#### ③ 읽기 전용(Read-Only) 객체는 Setter를 과감히 생략한다
실무 설계 시 외부에 데이터를 조회만 하도록 허용하고 변경을 막아야 하는 경우가 많습니다. 이때는 Getter만 만들고 Setter를 아예 구현하지 않음으로써 데이터의 변경 가능성을 차단하고 객체의 안전성을 높입니다.

### 3. 클래스 설계 공식 적용 예시 소스 코드
위의 공식을 적용하여 설계한 안전한 자바 클래스의 예시입니다.
```JAVA
public class UserAccount {
    // 1. 모든 필드는 private으로 은닉
    private String username;
    private int balance;

    // 생성자를 통한 필수 데이터 초기화
    public UserAccount(String username, int balance) {
        this.username = username;
        if (balance >= 0) {
            this.balance = balance;
        }
    }

    // 2. public Getter를 통해 안전하게 조회 기능 제공
    public String getUsername() {
        return this.username;
    }

    public int getBalance() {
        return this.balance;
    }

    // 3. public Setter 내부에 유효성 검사 로직을 넣어 데이터 무결성 보호
    public void setBalance(int balance) {
        if (balance < 0) {
            System.out.println("❌ 에러: 잔액은 0원 이상이어야 합니다. 변경이 거부되었습니다.");
            return; // 비정상적인 데이터 주입 차단
        }
        this.balance = balance;
    }
}
```

## Q3. 하나의 자바 소스 파일(.java) 내부에서 최상위 클래스(Outer Class)를 여러 개 정의할 때 접근 지정자와 관련하여 준수해야 하는 문법적 규칙은 무엇인가?
###1. public 클래스는 단 하나만 존재해야 합니다
- 규칙: 하나의 자바 소스 파일 안에서 public 접근 제한자가 붙은 최상위 클래스는 오직 한 개만 존재할 수 있습니다.
- 이유: 자바 컴파일러는 public 클래스의 이름과 소스 파일의 이름이 대소문자까지 완벽하게 일치할 것을 요구하기 때문입니다. 만약 한 파일에 public 클래스가 2개 이상 존재하면 소스 파일명을 어떤 클래스에 맞춰야 할지 모호해지므로 컴파일 에러가 발생합니다.

### 2. 다른 최상위 클래스들은 반드시 default 제한자여야 합니다
- 규칙: public 클래스를 제외한 나머지 최상위 클래스들에는 public, protected, private을 붙일 수 없으며, 접근 제한자를 생략한 default(package-private) 상태여야 합니다.
- 범위: 이렇게 생성된 default 클래스들은 동일한 패키지 내부에서만 접근하고 사용할 수 있게 제한됩니다.

### 3. public 클래스가 아예 없을 수도 있습니다
- 규칙: 자바 소스 파일 내부에 public 클래스가 단 하나도 존재하지 않는 설계도 문법적으로 가능합니다.
- 파일명: 파일 내에 public 클래스가 없다면, 소스 파일의 이름은 내부에 정의된 여러 default 클래스 중 아무 클래스의 이름으로나 지정해도 컴파일에 문제가 없습니다.

## Q4. 자바에서 protected 접근 지정자와 default 접근 지정자가 다른 패키지의 클래스를 대할 때 나타나는 결정적인 차이점은 무엇인가?
결정적인 차이점은 '상속 관계(IS-A 관계)에 있는 자식 클래스에게 접근을 허용하느냐'의 여부

### 🔒 1. default (package-private) 접근 지정자
- 타 패키지에서의 규칙: 다른 패키지에 존재하는 클래스라면, 상속 관계 여부와 상관없이 무조건 접근이 불가능(X)합니다.
- 본질: 오직 자신이 속한 패키지(가방) 안에서만 부품으로 공유하겠다는 의미입니다.

### 🛡️ 2. protected 접근 지정자
- 타 패키지에서의 규칙: 패키지가 다르더라도, 해당 클래스를 상속받은 자식 클래스(Subclass)라면 예외적으로 접근을 허용(O)합니다.
- 본질: 패키지가 다른 외부에는 숨기고 싶지만, 내 피를 물려받은 자식 클래스에게는 유산으로 물려주어 기능을 확장(Override 등)할 수 있도록 길을 열어주는 것입니다.

## Q5. 클래스의 생성자(Constructor)에 private 접근 지정자를 붙이는 이유와 이를 활용한 대표적인 디자인 패턴의 명칭을 서술하시오.
### 1. 생성자에 private 접근 지정자를 붙이는 이유
보통 생성자는 외부에서 객체를 생성(new)할 수 있도록 public으로 열어두는 것이 일반적입니다. 하지만 생성자를 private으로 닫아버리면 외부 클래스에서 new 키워드를 사용해 인스턴스를 직접 생성하는 것이 불가능해집니다.

실무에서 이러한 제약을 거는 이유는 다음과 같습니다.

- 객체 생성 횟수의 철저한 제한: 프로그램 전체에서 인스턴스가 단 하나만 존재해야 하거나, 개발자가 의도한 특정 방식을 통해서만 객체가 생성되도록 강제하기 위함입니다.
- 무분별한 객체 생성 방지: 인스턴스를 무분별하게 새로 만들면 메모리 낭비가 심해지거나 객체 간의 데이터 정합성이 깨질 수 있는 시스템에서 이를 구조적으로 방어합니다.
- 유틸리티 클래스의 인스턴스화 차단: Math 클래스처럼 상태(인스턴스 필드)가 없고 오직 static 메소드만 제공하는 클래스의 경우, 객체를 생성하는 것 자체가 의미가 없으므로 private 생성자로 인스턴스화를 원천 차단합니다.

- **Q2. 접근 지정자를 아예 생략하여 같은 패키지 내에 위치한 클래스들 사이에서만 참조가 가능하도록 선언하려 한다. 자바 표준 문법 명세에서 이 접근 지정 상태를 부르는 이름을 쓰시오.**Java
    

        설명: 자바에서는 접근 지정 키워드를 명시하지 않았을 때 자동으로 `default` 제어 상태가 되며, 이는 같은 디렉터리(패키지) 내 클래스들끼리의 협력 모듈을 구성할 때 주로 사용된다.
        
- **Q3. private으로 은닉된 멤버 변수 `id`의 값을 외부 시스템에 단순히 안전하게 리턴해 주는 일종의 읽기 전용 통로인 Getter 메서드를 자바 표준 관례에 맞게 작성하시오.**Java
    
    ```
    public class Member{

        // 여기에 id 변수에 대한 Getter 메서드를 작성하시오.
    }
    ```
    
    - 완전한 소스 코드:Java
        

        설명: Getter 메서드는 외부에서 읽을 수 있어야 하므로 `public` 접근 범위를 지녀야 하며, 반환 타입은 필드 변수와 매칭하고 이름은 `get+필드명` 형태로 구성하는 것이 실무 명세 관례이다.

        
        설명: 시스템 아키텍처 상 진입점이 되거나 공통 유틸리티 등 다른 패키지에서 경계 없이 호출되어야 하는 클래스 파일은 클래스 명칭 맨 앞에 `public`을 명시해야만 한다.
        
- **Q6. 자바의 문법 규칙상 생성자를 private으로 막고 단 하나의 인스턴스만 공유하는 싱글톤 객체를 아래 소스 코드의 빈칸을 채워 마저 완성하시오.**Java
    
    ```
    public class DatabaseConnection{
        private static DatabaseConnection instance = new DatabaseConnection();
    
        // 인스턴스의 외부 생성을 전면 제한하는 생성자 정의
        [       ] DatabaseConnection() { }
    
        public static DatabaseConnection getInstance(){
            return instance;
        }
    }
    ```
    
    - 완전한 소스 코드:Java
        
        ```
        public class DatabaseConnection{
            private static DatabaseConnection instance = new DatabaseConnection();
        
            private DatabaseConnection(){ }
        
            public static DatabaseConnection getInstance(){
                return instance;
            }
        }
        ```
        
        설명: 생성자 헤더 공간에 `private` 제어자를 선언하면 외부에서 `new DatabaseConnection()` 구문을 실행할 때 컴파일 에러가 발생하므로, 클래스 내부에서 미리 생성해 둔 유일한 인스턴스를 안정적으로 제공할 수 있다.
        
- **Q7. Setter 메서드 작성 시 매개변수명과 클래스 내부의 멤버 변수명이 동일하게 설정될 경우, 로컬 변수가 아닌 클래스의 필드 자원을 정확히 매핑하여 가리키기 위해 사용하는 특수 키워드를 작성하시오.**Java
    
    ```
    public class Product{
        private String name;
    
        public void setName(String name){
            [        ].name = name;
        }
    }
    ```
    
    - 완전한 소스 코드:Java
        
        ```
        public class Product{
            private String name;
        
            public void setName(String name){
                this.name = name;
            }
        }
        ```
        
        설명: 메서드 내부의 매개변수가 멤버 변수와 동명일 때, 힙 영역에 생성된 인스턴스 자기 자신의 주소를 명시적으로 포인팅하여 쉐도잉 현상을 피하게 만드는 키워드는 `this`이다.
        
- **Q8. 패키지가 전혀 다른 외부 영역에 위치하지만, 상속 관계(extends)에 놓여 있는 하위 자식 클래스 구조 안에서만큼은 부모의 변수를 자유롭게 호출할 수 있도록 열어주는 접근 지정 키워드를 적으시오.**Java
    
    ```
    package com.parent.package;
    
    public class Parent{
        [          ] String legacyData;
    }
    ```
    
    - 완전한 소스 코드:Java
        
        ```
        package com.parent.package;
        
        public class Parent{
            protected String legacyData;
        }
        ```
        
        설명: `protected` 접근 지정자는 default 수준의 패키지 경계 보호막을 유지하되, 객체지향의 상속 확장을 고려하여 다른 패키지에 입지한 자식 클래스에게만 특별히 데이터 접근 권한을 상속해 준다.
        
- **Q9. 개발자가 정밀하게 설계한 내부 전용 헬퍼 함수 `calculateTax()`를 private으로 은닉하고, 대신 외부 시스템에는 다듬어진 최종 결과 인터페이스인 public 메서드 `getInvoice()`만을 제공하려 한다. 실무적 아키텍처 관점에서 이러한 방식으로 내부 구현을 접근 제한 구역으로 숨겼을 때 얻을 수 있는 대표적인 설계상 이점을 서술하시오.**Java
    
    ```
    public class TaxEngine{
        private double calculateTax(int price){ return price * 0.1; } // 내부 격리
        public double getInvoice(int price){ return price + calculateTax(price); } // 개방
    }
    ```
    
    - 완전한 소스 코드:Java
        
        ```
        // 아키텍처 유지보수 예시
        public class TaxEngine{
            // 내부 과세 정책이 바뀌어 이 함수를 대폭 수정하더라도 외부 결합도는 유지된다.
            private double calculateTax(int price){ return price * 0.15; }
            public double getInvoice(int price){ return price + calculateTax(price); }
        }
        ```
        
1. 외부 코드와의 결합도(Coupling) 최소화 및 유지보수성 극대화
만약 calculateTax()가 public으로 열려 있어서 수십 개의 외부 클래스에서 이 메서드를 직접 가져다 쓰고 있었다면, 세율을 0.1에서 0.15로 바꾸거나 내부 계산 수식을 전면 수정할 때 이 메서드를 사용하던 다른 팀원들의 외부 코드까지 도미노처럼 컴파일 에러가 발생하거나 오작동하게 됩니다.

세부 구현을 private으로 숨기면 내부 로직을 아무리 대폭 수정하거나 완전히 갈아엎더라도, 외부 시스템은 그 사실을 전혀 모른 채 언제나 동일한 getInvoice()만 호출하면 되므로 시스템 전체의 변경 폭과 유지보수 비용이 획기적으로 줄어듭니다.

2. 객체의 자율성 보장과 잘못된 접근 방지 (오용 차단)
세금 계산 방식(calculateTax)은 TaxEngine이라는 객체 스스로가 가장 잘 알고 처리해야 하는 '내부 비밀'입니다. 외부 클래스가 이 내부 함수에 직접 개입하여 가공되지 않은 중간 연산 값을 임의로 가로채거나 조작하는 것을 문법적으로 차단합니다.

이로 인해 외부 개발자가 코드를 잘못 가져다 써서 발생할 수 있는 비즈니스 로직상의 결함이나 데이터 오염(오용)을 원천 봉쇄할 수 있습니다.

3. 단순하고 직관적인 인터페이스 제공 (복잡도 감소)
외부 시스템 입장에서는 영수증 최종 금액(getInvoice)만 알면 될 뿐, 내부에서 세금을 10%를 때리는지 15%를 때리는지, 혹은 우대 세율이 어떻게 적용되는지 등의 복잡한 인프라나 연산 과정을 알 필요가 없습니다.

불필요한 내부 동작을 private으로 감춤으로써 이 객체를 사용하는 다른 팀원들에게 가장 깔끔하고 이해하기 쉬운 최소한의 API만 노출하게 되므로, 프로젝트 전체의 인지적 복잡도가 내려갑니다.

💡 면접관을 사로잡는 한 줄 요약
"구체적인 변경 가능성이 높은 내부 구현(calculateTax)을 private으로 격리하고, 변하지 않는 추상적인 결과 인터페이스(getInvoice)만 public으로 개방함으로써, 외부 코드의 수정을 유발하지 않고도 내부 정밀도를 안전하게 확장할 수 있는 느슨한 결합(Loose Coupling) 아키텍처를 달성할 수 있습니다."
