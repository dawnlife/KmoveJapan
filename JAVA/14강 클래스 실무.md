# 🏗️ Java 실무: 견고한 클래스 설계와 객체 생성을 위한 체크리스트

### 1. 필드 선언 시 접근 제한자를 습관적으로 public으로 설정할 때 발생하는 실무적인 문제는 무엇인가?
  - #### 데이터 무결성(Data Integrity) 훼손
    - public 필드는 외부의 모든 클래스에서 아무런 제어 없이 직접 접근하여 값을 변경할 수 있습니다.

    - 문제점: 나이(Age) 필드에 마이너스(-) 값이 들어가거나, 계좌 잔액이 조작되거나, 필수 객체에 null이 할당되는 등 비정상적인 데이터가 주입되는 것을 시스템 차원에서 방어할 수 없습니다.

    - 해결책: 필드를 private으로 제한하고 Setter 메서드를 통하게 만들면, 내부에 유효성 검사(Validation) 로직을 추가하여 항상 안전하고 유효한 상태의 데이터만 유지할 수 있습니다.

  - #### 강한 결합도(Tight Coupling)로 인한 유지보수성 악화
    - 클래스의 내부 구현 상태가 외부에 그대로 노출되면, 외부의 수많은 코드들이 해당 필드에 강하게 의존하게 됩니다.

    - 문제점: 향후 비즈니스 요구사항이 변경되어 내부 필드의 데이터 타입(예: int를 String으로 변경)이나 변수명을 수정해야 할 때, 이 필드를 직접 참조하고 있는 프로젝트 외부의 모든 코드를 찾아내어 수정해야 합니다. 이는 유지보수 비용을 기하급수적으로 높이고 버그 발생 확률을 키웁니다.

  - #### 상태 추적 및 디버깅의 어려움
    - 시스템에 버그가 발생하여 특정 객체의 데이터가 오염되었을 때, 그 원인을 찾기가 극도로 어려워집니다.

    - 문제점: 시스템 곳곳에 흩어진 수십 개의 클래스가 하나의 public 필드에 동시다발적으로 접근해 값을 덮어쓴다면, "언제, 어디서, 누가" 이 값을 변경했는지 추적(Tracking)하는 것이 거의 불가능해집니다. 반면 메서드를 통하게 하면 중단점(Breakpoint)을 걸어 쉽게 추적할 수 있습니다.
  - #### 읽기/쓰기 권한의 세부 제어 불가
    - 실무적인 아키텍처 설계에서는 특정 데이터를 '읽기 전용'으로만 외부에 제공하거나, 반대로 '쓰기 전용'으로 만들어야 하는 경우가 빈번합니다.

    - 문제점: 필드를 public으로 선언해버리면 무조건 읽기와 쓰기가 동시에 전면 허용됩니다. Getter만 생성하여 외부에 읽기 권한만 부여하는 식의 유연하고 안전한 접근 제어가 불가능해집니다.

### 2. 생성자(Constructor) 내부에 DB 연결이나 외부 API 호출과 같은 무거운 로직을 포함했을 때의 위험성은 무엇인가?
  - #### 단위 테스트(Unit Test)의 어려움
    - 생성자에 무거운 외부 의존성이 포함되어 있으면, 이 객체를 격리하여 테스트하는 것 자체가 고통이 됩니다.

    - 문제점: 객체의 순수한 비즈니스 로직만 테스트하고 싶어도, 객체를 생성(new)하는 순간 무조건 실제 DB나 API에 연결을 시도하게 됩니다. 테스트용 가짜 객체(Mock)를 주입하기가 극도로 어려워져, 테스트 속도가 현저히 느려지고 외부 환경(네트워크 상태 등)에 따라 테스트 결과가 불안정해집니다.

  - #### 예외 처리(Exception Handling)의 복잡성
    - 객체 생성은 인스턴스를 메모리에 할당하고 초기 상태를 세팅하는 단순하고 '안전한' 작업이어야 합니다.

    - 문제점: 생성자에서 DB 연결이나 네트워크 통신을 하다가 실패(Timeout 등)하면 예외가 발생합니다. 생성자에서 던져진 예외는 흐름 제어를 까다롭게 만들며, 초기화가 중단된 불완전한 상태의 객체(Partially Constructed Object)가 발생하여 예기치 않은 치명적인 버그를 유발할 수 있습니다.

  - #### 단일 책임 원칙(SRP) 위반
    - 클래스는 자신이 맡은 본연의 역할(도메인 로직)에만 집중해야 합니다.

    - 문제점: 하나의 객체가 '자신의 상태 초기화'뿐만 아니라 'DB 커넥션 관리', '네트워크 통신'이라는 무거운 책임까지 동시에 떠안게 됩니다. 이는 코드를 비대하게 만들고, 커넥션 방식이나 API 스펙이 변경될 때 전혀 상관없는 도메인 객체의 코드까지 수정해야 하는 강한 결합도를 낳습니다.

  - #### 성능 저하 및 블로킹(Blocking)
    - 문제점: 객체를 생성하는 데 수백 밀리초(ms)에서 수 초가 걸리게 됩니다. 시스템 내부에서 해당 객체를 여러 번 반복해서 생성해야 한다면, 애플리케이션의 스레드가 외부 I/O를 기다리느라 멈추게 되고(Blocking) 심각한 성능 병목(Bottleneck) 현상으로 직결됩니다.

### 3. 클래스 간의 관계를 맺을 때 상속(Inheritance)을 단순한 코드 재사용 수단으로 오용하면 어떤 문제가 생기는가?
  - #### 캡슐화 파괴와 깨지기 쉬운 기반 클래스 (Fragile Base Class)
    - 상속은 하위 클래스가 상위 클래스의 내부 구현 세부사항에 강하게 의존하게 만듭니다.
    - 문제점: 상위 클래스의 코드가 수정되면, 그 변경 여파가 하위 클래스들로 통제할 수 없이 퍼져나갑니다. 상위 클래스의 메서드 로직이 조금만 바뀌어도 하위 클래스에서 예상치 못한 버그가 발생하며, 이는 객체지향의 핵심인 캡슐화(カプセル化)를 완전히 무너뜨립니다.
  - #### 불필요한 인터페이스의 강제 노출
    - 상속을 받으면 상위 클래스의 모든 public 메서드를 하위 클래스도 그대로 외부로 노출하게 됩니다.
    - 문제점: 하위 클래스의 도메인 성격과 전혀 맞지 않는 기능까지 외부에서 접근할 수 있게 됩니다. 대표적인 예로, Java의 초기 라이브러리인 Stack이 Vector를 상속받은 탓에, 스택의 중간에 임의로 요소를 밀어 넣는(Vector의 기능) 비정상적인 조작이 가능해져 데이터 무결성이 훼손되는 문제가 있었습니다.
  - #### 유연성 및 확장성 상실 (단일 상속의 한계)
    - Java나 C# 같은 대부분의 현대 언어는 클래스의 단일 상속(Single Inheritance)만 지원합니다.
    - 문제점: 단순한 코드 재사용을 위해 이 소중한 '단일 상속권'을 소모해버리면, 정작 나중에 도메인 모델링 상 정말로 상속받아야 할 중요한 부모 클래스가 생겼을 때 상속 구조를 적용할 수 없게 됩니다.

  - #### 강한 결합도 (Tight Coupling)
    - 상속은 컴파일 타임에 결정되는 가장 강한 형태의 결합입니다.
    - 문제점: 런타임에 동적으로 동작을 변경하거나 교체하는 것이 불가능해집니다. 이는 요구사항 변화에 민첩하게 대응해야 하는 현대의 실무 개발 환경에서 치명적인 단점으로 작용합니다.

### 4. 클래스 내부에서 필드(인스턴스 변수)를 초기화하지 않고 사용할 때 초보자들이 가장 많이 겪는 런타임 에러는 무엇인가?
  - #### 초기화되지 않은 참조 변수(Reference Variable)의 실체
    - Java나 C# 같은 객체지향 언어에서 클래스 내부의 필드를 선언만 하고 객체를 할당(new)하지 않으면, 해당 필드에는 실제 메모리 주소가 아닌 null(아무것도 가리키지 않음)이 기본값으로 들어갑니다.
    - 에러 발생 순간: 이 null 상태인 변수에 점(.)을 찍고 내부 메서드를 호출하거나(예: user.getName()) 필드에 접근하려 하는 순간, 가리킬 실제 객체가 메모리에 없기 때문에 즉시 NullPointerException이 발생하며 프로그램이 비정상 종료(Crash)됩니다.
  - #### NPE가 실무에서 치명적인 이유
    - NPE는 컴파일 타임(코드 작성 중)에는 쉽게 발견되지 않고, 프로그램이 실행되는 도중(런타임)에 특정 조건이 맞을 때 갑자기 터지는 폭탄과 같습니다.
    - 데이터베이스에서 가져온 값이 의도치 않게 비어있거나,
    - 외부 API 응답에서 특정 필드가 누락되었을 때 이를 초기화/방어하는 로직이 없다면, 서비스 전체가 마비되는 심각한 장애로 직결됩니다.
---
  - #### 생성자(Constructor)를 통한 확실한 초기화:
    - 객체가 생성(new)되는 순간, 필수적인 모든 필드는 생성자를 통해 반드시 유효한 값이나 객체로 초기화되어야 합니다. "불완전한 상태의 객체"  가 시스템에 돌아다니지 않도록 원천 차단하는 것이 중요합니다.
  - #### 캡슐화(Encapsulation)를 통한 외부 조작 방지:
    - 필드를 public으로 열어두어 외부에서 실수로 null을 주입하는 일이 없도록 , 필드는 철저히 private으로 닫고  검증된 데이터만 들어오도록 설계해야 합니다.

### 5. 객체지향 설계 원칙 중 하나인 '단일 책임 원칙(SRP)'을 무시하고 만든 '갓 클래스(God Class)'가 실무에서 기피되는 이유는 무엇인가?
  - #### 극단적인 병합 충돌(Merge Conflict)과 협업 병목
    - 문제점: 여러 개발자가 각자 다른 기능(예: 결제, 유저 인증, 상품 검색)을 개발하더라도, 결국 갓 클래스라는 하나의 동일한 파일에 접근하여 코드를 추가하고 수정해야 합니다. 이로 인해 Git과 같은 버전 관리 시스템에서 끊임없이 병합 충돌이 발생하며, 개발 자체보다 코드를 합치고 충돌을 해결하는 데 더 많은 시간과 에너지를 낭비하게 됩니다.
  - #### 깨지기 쉬운 시스템 (나비효과)
    - 문제점: 하나의 클래스 안에 수많은 기능이 혼재되어 있으면 내부 데이터와 로직들이 서로 강하게 결합(Tight Coupling)됩니다. 이 상태에서는 '유저 인증' 로직을 조금 수정했는데 전혀 상관없는 '상품 검색' 기능이 멈추는 식의 예기치 못한 버그가 꼬리를 물고 일어납니다. 결국 코드를 건드리는 것 자체가 두려워져 유지보수가 불가능한 레거시로 전락합니다.
  - #### 단위 테스트(Unit Test)의 불가능
    - 문제점: 수십 개의 외부 의존성을 가지고 수천 줄에 달하는 갓 클래스는 특정 기능만 격리하여 단위 테스트를 작성하는 것이 사실상 불가능합니다. 테스트 코드가 없으므로 리팩토링이나 기능 추가 시 시스템의 안정성을 담보할 수 없게 됩니다.
  - #### 가독성 저하 및 온보딩(Onboarding) 비용의 급증
    - 문제점: 신규 입사자나 다른 팀원이 프로젝트에 투입되었을 때, 수천 줄짜리 갓 클래스의 코드 흐름을 읽고 파악하는 데 엄청난 시간이 소요됩니다. 이는 팀 전체의 생산성을 심각하게 떨어뜨립니다.

### 6. 객체를 생성할 때 클래스 내부에서 다른 객체를 직접 new로 생성하여 사용하는 방식의 한계는 무엇인가?
  - #### 단위 테스트(Unit Test)의 고립성 파괴
    - 클래스 내부에서 new로 객체를 생성하면, 해당 객체는 코드 내부에 완전히 하드코딩(Hardcoding)됩니다.
    - 문제점: 해당 클래스의 순수한 비즈니스 로직만 테스트하고 싶어도, 내부에 숨겨진 의존 객체까지 함께 동작하게 됩니다. 이로 인해 테스트용 가짜 객체(Mock)를 주입하기가 극도로 어려워져, 테스트 속도가 현저히 느려지고 외부 환경에 따라 테스트 결과가 불안정해집니다.
  - #### 유연성 및 확장성 상실 (개방-폐쇄 원칙 위반)
    - new 키워드는 인터페이스(추상)가 아닌 구체적인 특정 구현체(클래스)에 직접 의존하겠다는 강력한 선언입니다.
    - 문제점: 향후 비즈니스 요구사항이 변경되어 기존 객체를 다른 객체로 교체해야 할 때 (예: MySQLRepository를 OracleRepository로 변경), 해당 객체를 new로 생성하고 있는 모든 클래스의 내부 코드를 직접 찾아가서 일일이 수정해야 합니다. 이는 코드를 수정에는 닫혀 있고 확장에는 열려 있어야 한다는 '개방-폐쇄 원칙(OCP)'을 정면으로 위반합니다.
  - #### 3. 단일 책임 원칙(SRP) 위반
    - 클래스는 자신이 맡은 본연의 도메인 로직 처리에만 집중해야 합니다.
    - 문제점: 하나의 객체가 자신의 본래 역할뿐만 아니라, 자신이 사용할 객체를 직접 생성하고 생명주기를 관리하는 책임까지 동시에 떠안게 됩니다. 책임이 비대해지면 코드가 복잡해지고 유지보수성이 크게 떨어집니다.

```
        sender.send("주문 완료");

}
```

  - #### public int totalAmount; (캡슐화 위반)
    - 데이터 무결성 파괴: 필드가 public으로 선언되어 외부의 모든 클래스에서 제어 없이 직접 접근할 수 있습니다. 누군가 실수로 order.totalAmount = -50000; 처럼 마이너스 값을 주입해도, 시스템 차원에서 이를 방어할 유효성 검사(Validation) 로직을 적용할 수 없습니다.
    - 상태 추적의 어려움: 여러 클래스가 이 필드에 동시다발적으로 접근해 값을 덮어쓰게 되면, 버그가 발생했을 때 "언제, 어디서, 누가" 값을 변경했는지 추적(Tracking)하는 것이 사실상 불가능해집니다.

  - #### OrderService() 생성자 내부의 무거운 로직 (DB 연결 시뮬레이션)
    - 성능 병목 및 블로킹: 객체를 생성(new OrderService())할 때마다 스레드가 2초(Thread.sleep(2000))씩 멈추게 됩니다. 객체 생성은 단순하고 안전한 초기화 작업이어야 하는데 , 무거운 로직이 포함되어 애플리케이션 스레드가 멈추고(Blocking) 심각한 성능 병목을 유발합니다.
    - 단위 테스트(Unit Test)의 고립성 파괴: 이 클래스의 순수한 로직만 테스트하고 싶어도, 객체를 생성하는 순간 무조건 무거운 연결 로직이 실행됩니다. 가짜 객체(Mock)를 주입하기 어려워지고 테스트 속도가 크게 저하됩니다.

  - #### new EmailSender(); (클래스 내부에서의 직접 생성 / 강한 결합)
    - 유연성 및 확장성 상실 (OCP 위반): OrderService가 EmailSender라는 특정 구현체에 강하게 결합(Tight Coupling)되어 있습니다. 향후 비즈니스 요구사항이 바뀌어 이메일 대신 'SMS 전송'이나 '카카오톡 전송'으로 변경해야 할 경우, 의존하고 있는 이 내부 코드를 찾아내어 직접 수정해야 하므로 개방-폐쇄 원칙을 정면으로 위반합니다.
    - 단일 책임 원칙(SRP) 위반: 클래스가 본연의 도메인 로직 처리뿐만 아니라, 사용할 객체를 직접 생성하고 관리하는 책임까지 떠안아 코드가 비대해집니다.
